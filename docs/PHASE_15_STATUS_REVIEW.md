# Status 现状与建议：分析，不改动结算

本阶段没有修改 StatusData、StatusInstance、EffectSystem 或 CombatSystem。以下按实际代码说明，不把未来示例写成现有功能。

## 配置与运行时

- `scripts/effects/status_data.gd` 的 StatusData 是只读 Resource：ID、中文说明、最大层数、默认持续回合、每层攻击/受伤/防护平坦修正、回合末伤害、跳过意图。
- StatusInstance 是 RefCounted：definition、stacks、remaining_turns。玩家的状态在当前 CombatState.statuses；敌人的在 EntityInstance.statuses。不是 PlayerState 的跨战斗状态。
- EffectData.APPLY_STATUS 指定配置、层数 amount 和可覆盖的 duration；0 使用默认持续时间。
- EffectSystem.add_status 按 ID 合并：层数相加至上限，持续时间取现有和新时长的较大值；不相加时长，没有独立层到期。expire 在每回合末扣一回合，归零移除。战斗清理时不带到下一场。

## 实际八种状态

| 状态 | 当前每层效果 |
| --- | --- |
| 虚弱 weak | 输出伤害 -2 |
| 暴露 vulnerable | 受到伤害 +2，并非翻倍 |
| 灼伤 burn | 回合末直接失去 1 HP，绕过防护 |
| 失衡 stun | 敌人跳过当前意图，默认 1 回合 |
| 专注 focused | 输出伤害 +2 |
| 稳固 braced | 每次获得防护 +2 |
| 躁怒 enraged | 下次锁定意图的输出伤害 +2 |
| 流血 bleed | 回合末直接失去 1 HP，数值机制与灼伤相同 |

中毒、移动减速、通用玩家眩晕尚未实现。游戏没有实时移动速度；不要为“灼烧减速”虚构此属性。敌人失衡不能直接推断为玩家少行动点：当前 skip_intent 的消费者只有敌人意图阶段。

## 触发与配合

CardData、EntityActionData 和 WeaknessData 都提供有限 EffectData。卡牌结算、敌人意图和实体反应可施加状态，先作用于私有 CombatState 副本，随后提交。EntityReaction 的实际类为 WeaknessData，它按 TriggerData 和 ConditionData 触发；不是 Status 自带通用监听器。

回合顺序明确写在 CombatSystem.plan_end_turn：实体回合末反应 → 未退出实体执行当前锁定意图（先检查失衡）→ 玩家及实体持续伤害 → 胜负 → 状态时长递减/移除 → 回合/AP/防护清理 → 回合开始反应 → 锁定新意图 → 抽牌与装备机会。

玩家伤害在执行时读取输出状态；敌人输出加成在锁定意图时固化，实际执行不会再加一遍。受伤修正在命中时读取。于是敌人刚被施加虚弱，不会悄悄改掉已经公开的当前意图，只影响后续锁定。状态生效和 UI 说明需要明确这种差异。

## 当前问题 / 风险

1. burn 与 bleed 是不同内容身份、同一种持续伤害机制，属于数据复用，不需要各建一个 System。
2. skip_intent 名义上存在共用状态模型，但目前只处理敌人；未来设计玩家控制效果时必须单独确认如何影响出牌/AP，不能假定天然对称。
3. 一个状态的所有层共享计时；叠层并刷新可能让旧层长时间保留。若未来中毒层各自到期，当前结构不足，需先确定规则。
4. 新增状态组合目前仍靠有限字段；不宜现在引入任意脚本回调。效果内部按字段名汇总是集中实现，不是完整属性修改器系统。
5. 攻击加成的锁定时机与玩家直接效果不同，需要测试和提示；现有约定优先保证公开意图不变化。尤其是玩家行动时施加给敌人的 1 回合虚弱：当前意图已锁定，下一次锁定前状态又到期，可能完全没有削弱攻击。此风险应在后续确定计时规则时解决，本阶段没有擅自改变公开意图或到期顺序。
6. 玩家和敌人状态目前都用文本显示名称、层数和剩余回合；尚缺统一图标与完整规则说明。图标素材、悬停触发时机说明可作为后续独立 UI 任务，不需要重建状态所有者。
7. 持续伤害遍历当前全部实体，没有单独跳过已退去者。若退去和 DOT 致死同回合发生，最终状态可能变为 DEFEATED；需在未来明确“离开即停止状态结算”还是“本轮仍结算”，加入专门测试后再改。

## 推荐后续设计（待确认后独立实现）

- 分类标签 Buff / Debuff / Control / DOT / Special 仅用于筛选、图标和净化规则，不按分类建立五套运行时所有者。
- 静态配置明确叠加方式（加层/替换/取最大）、刷新方式（不刷新/取较长/重置）和单一持续时间。先保留共享计时，避免未经确认引入独立每层实例。
- 统一少量触发点：回合末持续效果、伤害前修正、意图执行前控制。以后确有需求再增加事件；不建立全局万能事件总线。
- 玩家和实体复用同一 StatusInstance 与汇总/到期工具；HP、AP 和意图仍交给各自领域提交，状态对象不直接改 UI 或任意 RunState。
- DOT 的时机与绕防护与否必须在说明中公开。中毒/灼烧可复用伤害机制再加有限环境标签；现在不决定数值。
- 易伤先评估平坦加伤与百分比在多段攻击中的差异；当前 +2 保持不变，不擅自改成翻倍。
- UI 统一展示图标/名称、层数、剩余回合、触发时机和简短效果。失衡需说明“跳过哪一次意图”，敌人攻击修正说明“影响下次锁定”。
- 失去追踪先判断是否应是实体行为状态/退出结局；需要计时的才考虑 Status。暴露弱点可复用现有受伤修正。异常同化是否跨战斗属于未决生命周期，不能默认塞进当前战斗状态或新增长期通用点数。

后续验收应包含：刷新与满层、同回合新施加状态的首次计时、失衡与退出的先后、DOT 双方同回合致死、锁定前后施加虚弱、失败动作不施加状态、战斗清理后不泄漏。此文不是授权立即改写这些规则。
